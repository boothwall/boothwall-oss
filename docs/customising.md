# Customising BoothWall

A wall is yours once you've changed two things: one config file and a handful of images. You shouldn't need to touch the app code.

## The config file

[`packages/shared/src/config/boothwall.config.ts`](../packages/shared/src/config/boothwall.config.ts) is read by the TV app, the web app and the API when they build. It's checked against a schema every time, so a typo fails the build instead of your booth.

The copy in the repo holds example values. Change at least `event` and `categories`, then run `pnpm boothwall setup`: it creates the Cloudflare resources and fills in `urls` and `deploy`. Setup stops if a configured database ID does not match the exact database name in your selected account. It never silently adopts another target or clears that ID.

### The `settings` field

Every field is optional; a missing one takes the default below.

| `uploadsClosedMessage` | "Uploads are closed for now. | `uploadsOpen`          | `true`                                                          | Whether guests can upload before anyone uses Control. | `playbackPaused`       | `false`                                                         | Whether the slideshow starts paused. As with `uploadsOpen`, the saved state wins once either Control switch has been used.                                                                                     |
| `showPicks`            | `true`                                                          | Every few minutes the wall opens a "Crowd favourite", a photo with at least three reactions. The standalone pages have no reaction buttons, so this only happens for reactions sent through the API.           |
| `eventEnded`           | `false`                                                         | Leave it out. `true` ends the event: uploads stop and the wall shows a thank-you screen whose QR code points at a recap page this edition doesn't serve.                                                       |

### Colours

Pick the colours you like. Text drawn on a brand colour is black or white, whichever reads better, and a brand colour used as text (a hashtag on the dark TV, a category on a white polaroid) is shaded just enough to stay readable.

Your colours apply to the universal theme, the phone pages and Control. The wedding, party and conference themes keep their own palettes on the wall (`WALL_PALETTES` in `packages/wall-ui/src/foundation/tokens/palette.ts`), so changing `theme.primary` doesn't change them.

`theme.primary` fills things: buttons, the glow around the selected photo. `theme.primaryOnDark` is the same accent as text on the dark wall and pages. The shipped tomato shows why there are two: `#CC4128` carries white labels on a button, but as text on the dark canvas it only reaches 3.9:1, so the hashtag and the year use `#FF6A4D` (6.7:1) instead.

The shared surface tokens distinguish guest/display pages from host tools. This app has three pages: the display and the guest page on the public side, Control on the host side.

### Wall themes

The wall has four themes selected through `settings.theme` in configuration, shared by the TV and browser renderer. **Universal** is the wall as it ships: your brand colours over the night sky. **Wedding** is a warm evening with fairy lights, gold sprigs and drifting petals; **party** a club with neon shapes, lasers and falling confetti; **conference** a main stage with spotlights sweeping over a glowing floor. The conference example picks `conference`.

To preview one without changing the config, open the browser wall with `?theme=` and its name, for example `/?theme=party`; an unknown name is ignored. **Next theme** in the Control panel steps the TV app and the browser wall through them. Both last until the app restarts or the page reloads.

A theme is four things: a palette (accent, partner colour, canvas and card tone) in `packages/wall-ui/src/foundation/tokens/palette.ts` (`WALL_PALETTES`), its art, the words on its join card (`JOIN_VOICE` in `packages/wall-ui/src/features/wall/constants/copy.ts`) and its name in `WALL_THEMES` (`packages/shared/src/settings/wall-settings/wall-settings.schemas.ts`). The art is drawn in code by `node scripts/themes/render.mjs` (needs rsvg-convert and ImageMagick): a backdrop with the still ornaments painted in, plus the few layers the wall moves on top (`features/wall/components/decor`). Movement stays slow and native-driven: one texture sliding or turning per layer, so the Fire TV Stick never redraws.

To add one, give it a name in `WALL_THEMES`, a palette, its words, its art and the corresponding renderer configuration support; TypeScript then points at every place that needs a value, and a test checks its text stays readable. Components never read a theme colour directly: they use `useWallTheme()` or `themedStyles()` from `foundation/theme/wallTheme.ts`, so a theme switch costs the TV nothing per frame.

### The default look

Out of the box the wall wears this edition's own look: BoothWall's open-source lockup (BoothWall with an OSS pill) top left with your event beside it, from `wall` in the config. The phone pages carry the same lockup. To make the wall yours, replace `lockup.png` with your own (or your sponsor's) lockup and `logo.png` with your event's logo. To go back to the classic header, with your logo top left and the count and Live beside it, remove `wall` (or set `header: "classic"`). The TV app and the web app read the look from the config; a host that embeds the shared wall passes it as `look`, and the wall stays classic without one.

The logos and the backdrop's twinkle layer are rendered from the SVGs in [`brand/`](../brand) (see its README for the commands); the app icons are exports of the same symbol. The backdrop itself is a night-sky image made with ChatGPT image generation. Keep it dark on the left, where the photos sit: the wall draws it as it is, with no dimming layer on top, and only two soft glows and the twinkle move over it. Keep the TV copy at 1920×1080, two pixels per dp, and the browser copy (`backdrop-web.jpg`) at 2880×1620, which stays sharp on a high-density screen. Only the universal theme draws them; the other three themes bring their own.

The demo photos (`demo-01` to `demo-24`) are booth scenes made with ChatGPT image generation, with made-up captions; they show no real people or events. Their captions and categories are in `packages/wall-ui/src/features/wall/data/demoPhotos.ts`. Swap in your own there, or leave them; they only show while `demo` is on or with `?demo` in the browser.

## Examples

[`examples/`](../examples) holds complete setups that mirror the repo layout. `pnpm boothwall example conference-booth` applies one, and `git checkout -- apps packages` undoes it. If you run BoothWall at your event, a pull request with your setup is welcome, as long as you're allowed to share the artwork.

## Existing saved settings

Fresh installations take presentation settings from the config. Existing plain database records retain their effective overrides until the explicit [settings authority migration](config-migration.md) is reviewed and applied. Back up the database and inspect `GET /settings` and its `X-BoothWall-Settings-Authority` header before an upgrade; do not delete saved settings to force a change. The basic Control page changes only durable playback and upload-intake state. See [older review settings](smart-moderation.md) for unsupported-provider migration decisions.

## Setup and safe reruns

`pnpm boothwall setup` validates configuration before contacting the provider, then shows the account ID, database, bucket, Worker names and custom domains before asking to continue. It checks exact database identity, bucket names and domain-zone ownership. If your login lists more than one account, set `CLOUDFLARE_ACCOUNT_ID` explicitly. The same account is pinned for every resource and deployment command.

Setup stores a local account/name binding in `apps/api/.dev.vars.setup.json` (gitignored). An interrupted run inspects and reuses matching resources; it does not delete data. A later run cannot silently switch the recorded account or wall name. Use a separate checkout for another stack. If the binding or a provider response is invalid, investigate before retrying rather than deleting the record to bypass the check.

The Control passcode stays in `apps/api/.dev.vars`, with owner-only permissions. Setup preserves existing values and unrelated lines; it never prints a generated passcode or overwrites one on a rerun. Read the file locally to obtain it. If an older local demo left an eight-digit passcode, explicitly replace it with a strong 12–256 character value before setup. Letters, digits and the documented safe punctuation are accepted; whitespace, quotes, backslashes and `#`/`$` are not accepted for a new passcode. Existing quoted or colon assignments are read with the provider’s dotenv rules; multiple `ADMIN_TOKEN` definitions stop setup instead of choosing the last value. Provider deployment output that may contain secrets is withheld from terminal errors.

`setup`, `deploy` and remote `migrate` confirm their target. After inspecting that target, automation may pass `--yes`; validation and account/resource checks still run. `migrate --local` uses only local state and never falls back to a remote operation. Unknown or repeated flags are errors.

On success, setup/deploy print the exact display, `/snap` and `/control` URLs. Configuration changes while a confirmation is open or between commands stop the operation. Keep database/storage backups independently; the local binding is not a backup.

Before applying migration `0009` to an existing installation, follow the [client fingerprint maintenance update](client-fingerprint-migration.md). It requires a separate random server key and drained traffic; the CLI does not create that maintenance window.

For an existing installation, follow the [saved-settings migration](config-migration.md): preview first, review and deploy the exact config patch, then explicitly apply it. Migration `0010` protects the retained original record and runtime flags; deploy alone never switches an old record to file authority.

## Serving the web app under a path

To put the wall on part of another site, give `urls.web` a path: `https://example.com/wall`. The web build then expects to be served from `/wall/`: its pages, `/wall/snap` and `/wall/control`, and every asset, link, redirect, install manifest and QR code carry the path. The API accepts requests from that site's origin.

- Serve the files from `apps/web`'s build output under that path, with a static host or a proxy, and answer any unknown address below it with the build's `index.html` so the pages load on reload.
- Match the path case-insensitively. The TV's "Scan for the source" QR is upper case, path included.
- `pnpm boothwall setup` and `deploy` publish the web app at the root of its own address, so they refuse a `urls.web` with a path. Host the build yourself instead.

## Your own TV build

The Vega TV app is source you build yourself. There is no store listing and no download: you build it with your own config and install it on your own TVs.

- It shows exactly one wall, the one in `tv.wallId`, at the API in `urls.api`. There is no code to enter and no menu on the TV. To show a different wall, change the config and rebuild.
- Everything in the config is bundled into the app. Anyone who has the built app can extract those values, including a display credential, so keep your build private and **never publish the `.vpkg`**.
- No build at all? Open the web wall in the TV's browser or on an HDMI stick instead.

## After a change

- **API or web app:** `pnpm boothwall deploy`.
- **TV:** rebuild and reinstall (`pnpm tv:build:release`, then `vega run-app …`). The config is bundled into the app, so a TV keeps the old values until you do.
